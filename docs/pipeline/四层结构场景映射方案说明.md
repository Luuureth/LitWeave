# 四层结构跨模态场景映射方案说明

## 1. 目标

本方案将原有的“原子事件直接匹配知识库，再做跨模态链接”升级为四层结构：

1. 原子事件 `atomic_event`
2. 场景事件 `scene_event`
3. 知识库规范事件 `kb_event`
4. 跨模态场景链接 `cross_modal_scene_link`

同时支持可选的 LLM 复核，用于：

- 复核 `scene_event -> kb_event` 的模糊映射
- 复核 `cross_modal_scene_links.json` 中置信度中等的链接

这样做的目的，是解决《红楼梦》文本事件与视频事件粒度不一致的问题：

- 文本通常是连续叙事块
- 视频通常是镜头块 / 场面块
- 直接 text ↔ video 往往过碎、过硬

因此先把原子事件聚成真实的 `scene_event`，再做知识库映射和跨模态链接，会更加稳定。

## 4. 四层结构设计

## 4.1 第一层：原子事件 `atomic_event`

来源于 `unified_events.csv`。

用途：

- 保留最细粒度证据
- 保留文本原文、视频来源路径
- 作为场景聚类的底层材料

本层不会直接作为最终跨模态结果的唯一主对象。

---

## 4.2 第二层：场景事件 `scene_event`

由原子事件在同一 `modality + source_id` 内聚类生成。

### 聚类依据

当前实现采用启发式聚类，满足以下条件之一时倾向合并到同一 scene：

- `narrative_order` 间隔不大于 `scene_max_gap`
- 前后原子事件匹配到同一个 `kb_event_id`
- 地点重合度较高
- 人物或地点的 Jaccard 重合度达到阈值

### 输出字段示例

- `scene_id`
- `scene_name`
- `scene_summary`
- `member_ueids`
- `member_count`
- `scene_characters`
- `scene_locations`
- `source_title`
- `source_path`
- `chapter_title` / `episode_title`

这样，场景事件就成为“文本连续叙事块 / 视频连续场面块”的中间层。

---

## 4.3 第三层：知识库规范事件 `kb_event`

场景事件不再直接 text ↔ video 比较，而是先映射到知识库事件。

### 匹配特征

当前实现综合以下因素：

- `scene_name / scene_repr_text` 与知识库 `事件名 + aliases`
- `scene_summary` 与知识库 `事件详情`
- 人物集合重合度
- 地点集合重合度
- 对 `is_cross_modal_anchor=1` 的知识库条目略作加权偏好

输出结果：

- `kb_event_id`
- `kb_event_name`
- `kb_top1_score`
- `kb_topk_candidates`
- `timeline_id`

---

## 4.4 第四层：跨模态场景链接 `cross_modal_scene_link`

当文本场景与视频场景匹配到同一个知识库事件时，会进一步生成跨模态链接。

### 核心思想

不是直接“文本原子事件 ↔ 视频原子事件”，而是：

- 文本原子事件 -> 文本场景
- 视频原子事件 -> 视频场景
- 文本场景 -> 知识库事件
- 视频场景 -> 知识库事件
- 共享同一个知识库事件，则形成 `cross_modal_scene_link`

### 链接中保留的信息

为便于你后续做前端，本次输出中保留了这些关键字段：

- `event_name`
- `canonical_event_name`
- `alignment_score`
- `text.representative.source_text`
- `text.chapter_title`
- `text.source_path`
- `video.video_source_path`
- `video.episode_title`
- `shared.timeline_id`
- `shared.characters`
- `shared.locations`

也就是说，你前端仍然可以像之前那样使用：

- `event_name`
- `source_text`
- `video_source_path`
- `chapter_title`
- `source_path`
- `timeline_id`

只是现在结构从一对一 pair 升级为“场景级链接 + 成员列表”。

## 5. LLM 复核设计

### 5.1 方案 A

已经先执行：

- 原子事件 -> 场景事件 -> 知识库事件 -> 跨模态链接

### 5.2 方案 B

已继续加入可选 LLM 复核：

#### 复核 1：`scene_event -> kb_event`

对模糊样本进行二次判定：

- 分数位于中间区间
- top1 与 top2 差距较小

LLM 只允许：

- 从给定候选知识库事件中选择一个
- 或判定为 `unmatched`

#### 复核 2：`cross_modal_scene_link`

对中等置信度链接进行二次判定：

- 是同一叙事场景 -> 保留 / 提升分数
- 不是同一叙事场景 -> 删除链接

### 5.3 使用方式

默认关闭 LLM：

```bash
python "跨模态事件对齐与事件时间线构建/run_kb_scene_mapping.py"
```

开启 LLM：

```bash
python "跨模态事件对齐与事件时间线构建/run_kb_scene_mapping.py" --enable-llm-review
```

如果开启 LLM，需要环境变量：

- `DASHSCOPE_API_KEY`

## 6. 输出文件说明

默认输出目录：

- `跨模态事件对齐与事件时间线构建/kb_outputs`

### 6.1 `atomic_events_with_kb.csv`

原子事件匹配知识库后的表格版结果。

用途：

- 查看每个原子事件映射到了哪个知识库事件
- 便于人工排查

### 6.2 `atomic_events_with_kb.json`

原子事件匹配知识库后的 JSON 版结果。

适合：

- 调试
- 前端备用
- 查看 `kb_topk_candidates`

### 6.3 `scene_events.json`

原子事件聚类后的场景事件结果，不含最终知识库映射。

适合观察：

- 场景切分是否合理
- 一个 scene 内包含哪些原子事件

### 6.4 `scene_events_with_kb.json`

场景事件匹配知识库后的结果。

每个 scene 包含：

- `scene_id`
- `scene_name`
- `member_ueids`
- `kb_event_id`
- `kb_event_name`
- `timeline_id`
- `kb_topk_candidates`

### 6.5 `kb_event_nodes.json`

知识库规范事件视角的聚合结果。

每个知识库事件节点记录：

- 映射到它的文本场景数量
- 映射到它的视频场景数量
- 观察到的人物 / 地点

可用于：

- 知识图谱节点展示
- 事件统计面板

### 6.6 `cross_modal_scene_links.json`

最终的跨模态场景链接结果。

这是前端最核心的结果文件。

每条链接大致结构：

## 9. 推荐使用顺序

推荐你按以下顺序使用：

### 第一步：不开 LLM，先看结构结果

```bash
python "跨模态事件对齐与事件时间线构建/run_kb_scene_mapping.py"
```

先重点检查：

- `scene_events.json`
- `scene_events_with_kb.json`
- `cross_modal_scene_links.json`

### 第二步：调 scene 聚类参数

如果发现场景切得过碎 / 过粗，优先调：

- `scene-max-gap`
- `scene-min-char-jaccard`
- `scene-min-loc-jaccard`

### 第三步：开启 LLM 复核

```bash
python "跨模态事件对齐与事件时间线构建/run_kb_scene_mapping.py" --enable-llm-review
```

这样可以重点提高：

- 模糊 scene -> kb 映射的正确率
- 中等置信度跨模态链接的精度

## 11. 总结

本次实现后的完整链路是：

`unified_events.csv`
→ 原子事件匹配知识库（粗匹配）
→ 原子事件聚类成 `scene_event`
→ `scene_event` 再匹配知识库（主匹配）
→ 文本 scene 与视频 scene 通过共享知识库事件建立链接
→ 可选 LLM 复核模糊映射与模糊链接
→ 输出面向前端使用的 JSON 结果

这套方案比直接做一对一对齐更适合《红楼梦》这样的长篇叙事文本与剧版改编对照场景。
