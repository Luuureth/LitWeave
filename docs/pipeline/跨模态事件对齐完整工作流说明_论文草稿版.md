# 跨模态事件对齐完整工作流说明（论文草稿版）

## 1. 研究目标与总体思路

本项目的目标，是在《红楼梦》文本叙事与 1987 版电视剧叙事之间建立可计算、可解释、可审计的跨模态事件对齐关系。这里的“跨模态”主要指两类来源：

1. 文本模态：`红楼梦文本/hongloumeng_txt_json/`
2. 视频模态：`剧版红楼梦/hongloumeng_json/`

研究的核心难点不在于“是否能做相似度匹配”，而在于：

- 文本与视频天然存在粒度不一致问题；
- 文本事件通常偏叙述摘要，视频事件通常偏镜头片段或场面块；
- 同一叙事事件在两个模态中的表达长度、顺序、细节密度、场景切分方式都不同；
- 如果直接做“文本事件 ↔ 视频事件”一对一匹配，容易出现大量误配、漏配和局部情节错位。

因此，本项目逐步形成了一条**由原子事件到场景，再到规范事件，再到跨模态链接**的工作路径。整个方案不是一次性设计完成，而是在多轮数据整理、知识库补充、结构重构和错误分析中逐步确定的。其核心思想是：

> 不直接让文本原子事件和视频原子事件彼此硬匹配，而是先通过场景事件与知识库规范事件建立稳定中介，再通过共享知识库事件构造跨模态场景链接。

换言之，本项目采用的不是简单的：

`text_atomic_event ↔ video_atomic_event`

而是更稳定的：

`text_atomic_event → scene_event → kb_event ← scene_event ← video_atomic_event`

最终对齐对象虽然以场景级链接呈现，但它背后保留了原始事件证据，因此既能服务于后续前端展示，也能满足论文中对“算法路径、可解释性、可回溯性”的要求。

## 2. 数据来源与基础输入

### 2.1 文本事件数据

文本侧数据位于：

- `红楼梦文本/hongloumeng_txt_json/`

该目录下每个 JSON 文件对应一个回目，包含：

- `chapter_id`
- `chapter_title`
- `event_count`
- `events`

其中 `events` 是事件列表，每条事件通常包括：

- `event_id`
- `narrative_order`
- `action`
- `characters`
- `location`
- `time_hint`
- `explicit_time`
- `relation_to_previous`
- `event_summary`
- `source_text`

这些字段既保留了叙事顺序，也保留了文本原文，是后续统一建模与可追溯展示的基础。

### 2.2 视频事件数据

视频侧数据位于：

- `剧版红楼梦/hongloumeng_json/`

该目录下每个 JSON 文件通常对应一个电视剧片段或分段场景，包含：

- `episode_id`
- `episode_title`
- `segment_id`
- `event_count`
- `events`

其中 `events` 与文本侧类似，也包含：

- `event_id`
- `narrative_order`
- `action`
- `characters`
- `location`
- `time_hint`
- `explicit_time`
- `relation_to_previous`
- `event_summary`

视频事件通常更接近镜头或场面片段，因此在粒度上往往比文本更细或者更局部。

### 2.3 统一原子事件层

为了在初始阶段实现文本与视频两端的统一建模，本项目构建了统一原子事件层：

- `unified_events/unified_events.csv`
- `unified_events/unified_events.json`

它们的字段结构基本一致，核心字段包括：

- `ueid`
- `modality`
- `source_id`
- `source_title`
- `event_id`
- `narrative_order`
- `action`
- `characters`
- `location`
- `time_hint`
- `explicit_time`
- `relation_to_previous`
- `event_summary`
- `source_text`
- `normalized_text`
- `semantic_core`
- `keywords`
- `source_path`

这里的 `unified_events` 的作用不是直接做最终匹配，而是作为：

- 两种模态的统一事件容器；
- 后续场景聚类的输入层；
- 保留细粒度证据来源的底层中间层。

### 2.4 事件知识库

为了避免文本事件名和视频事件名风格不统一、粒度不一致的问题，项目建立了规范事件知识库：

- `知识库/事件知识库/事件知识库.csv`

该知识库至少包含以下字段：

- `kb_event_id`
- `事件名`
- `event_aliases`
- `main_characters`
- `main_locations`
- `is_cross_modal_anchor`
- `timeline_ref`
- `事件详情`

这个知识库不直接替代原始事件，而是作为**规范叙事事件层**，承担“语义锚点”的作用。

### 2.5 地点知识库

在数据清洗阶段，项目还建立了地点知识库：

- `知识库/地点知识库/location_kb.json`
- `知识库/地点知识库/红楼梦地点表.csv`

地点知识库最初用于探索 location 归一，但在后续分析中发现：如果对源事件的地点做过强归并，会影响场景切分的质量。因此当前更合理的策略是：

- 保持源数据 location 的原始粒度；
- 将地点知识库主要作为参考知识与后续派生层使用；
- 场景切分结果优先服从人工审阅后认为“叙事上合理”的 scene_event。

这一经验对论文很重要，因为它说明：

> 数据规范化并不是越强越好。对于叙事场景划分任务，过度归一化反而可能损伤事件边界。

## 3. 工作流演化：从三层结构到四层结构

本项目的方法并不是一开始就固定，而是经历了如下演化。

### 3.1 初始思路：原子事件直接统一

最初的工作以 `unified_events` 为中心，尝试在文本和视频统一原子事件层面上进行相似度匹配。但很快发现：

- 原子事件过于细碎；
- 很多场景需要多个连续原子事件共同表达；
- 视频与文本即便叙事上对应，也不一定表现为同数量、同粒度的事件块。

因此，单纯的原子事件层对齐不足以支撑稳定的跨模态匹配。

### 3.2 三层结构：原子事件 → 知识库事件 → 跨模态链接

随后形成了“三层结构”：

1. 原始原子事件层
2. 知识库规范事件层
3. 跨模态场景映射层

基本思想是：

- 文本事件先匹配到知识库事件；
- 视频事件也先匹配到知识库事件；
- 如果它们映射到同一个知识库事件，则认为它们属于同一叙事簇。

这一步已经比“文本直接匹配视频”稳定很多，但仍然存在一个问题：

> 原子事件的粒度仍然太碎，不适合作为最终的跨模态对齐单元。

### 3.3 四层结构：原子事件 → 场景事件 → 知识库事件 → 跨模态链接

因此，本项目最终形成了四层结构：

1. **原子事件 atomic_event**
2. **场景事件 scene_event**
3. **规范事件 kb_event**
4. **跨模态场景链接 cross_modal_scene_link**

该结构的逻辑是：

- 先从统一原子事件层出发；
- 将原子事件聚合成叙事上更稳定的 scene_event；
- 再让 scene_event 去匹配 kb_event；
- 最后让文本 scene 与视频 scene 通过共享 kb_event 建立链接。

这个结构的优势在于：

- 保留原始证据；
- 对齐粒度更接近真实叙事单元；
- 规范事件作为中介，增强可解释性；
- 最终跨模态结果更适合前端展示与论文分析。

## 4. 原子事件层的统一与表示

### 4.1 统一字段

无论事件来自文本还是视频，都被统一到一套字段中。这样做的目的，是为后续相似度计算与聚类提供统一特征空间。

### 4.2 原子事件语义表示

在代码中，原子事件会构造成一个用于相似度建模的文本表示 `event_repr_text`。表示由以下部分拼接而成：

- 动作：`action`
- 摘要：`event_summary`
- 语义核：`semantic_core`
- 人物：`characters`
- 地点：`location`
- 关键词：`keywords`

典型形式类似：

- `动作:商议薛宝钗生日规格；摘要:凤姐与贾琏商议寿宴规格；人物:贾琏、王熙凤；地点:凤姐院；关键词:宝钗生日、寿宴`

这种表示的设计动机是：

1. 不单看事件名；
2. 同时利用结构化角色、地点信息；
3. 为语义匹配提供较高信息密度的输入文本。

---

## 5. 场景事件（scene_event）构建

场景事件是本项目最关键的中间层。

### 5.1 构建动机

一个原子事件通常只表示一个动作片段，例如：

- 点戏
- 讲曲文
- 说笑
- 递戏单

但真正的叙事场景往往是多个连续动作共同构成的，例如：

- 宝钗生日宴上的点戏、讲解曲文、宝玉入迷
- 黛玉葬花前后的误会、见落花、吟《葬花吟》
- 晴雯撕扇前后的争执、哄笑、撕扇取乐

因此，要想稳定对齐文本与视频，就必须先把多个原子事件聚成更接近叙事真实单位的 `scene_event`。

### 5.2 场景聚类的启发式规则

在 `kb_scene_mapping_pipeline.py` 中，scene_event 的构建采用启发式聚类方法，主要依据如下特征：

1. **同源约束**
   - 只在同一个 `modality + source_id` 内聚类；
   - 不跨章节、不跨视频段聚类。

2. **叙事顺序连续性**
   - 利用 `narrative_order` 判断事件是否连续；
   - 若前后事件顺序间隔不大于阈值（如 `scene_max_gap=2`），则倾向于归并。

3. **人物重合度**
   - 计算相邻事件人物集合的 Jaccard 相似度；
   - 如果角色重叠较高，则说明两事件可能属于同一场景。

4. **地点重合度**
   - 计算地点集合 Jaccard 相似度；
   - 若地点一致或近似，则更可能属于同一场景。

5. **语义相似度**
   - 使用文本相似度比较相邻事件的语义表示；
   - 结合摘要和动作名判断是否应合并。

6. **知识库粗匹配先验**
   - 若原子事件已经粗略映射到同一个知识库规范事件，也会增强合并倾向。

### 5.3 scene_event 结果字段

生成的 `scene_events.json` 中，每条 scene 包含：

- `scene_id`
- `modality`
- `scene_name`
- `scene_summary`
- `source_id`
- `source_title`
- `source_path`
- `member_ueids`
- `member_count`
- `timeline_id`
- `scene_characters`
- `scene_locations`
- `chapter_id / chapter_title`
- `episode_id / episode_title`

### 5.4 场景切分结果的人工选择

在后续分析中，项目发现：

- 如果重新依赖 `unified_events` 和最新 location 状态反复重跑，scene 切分会受到影响；
- 某些地点字段被过粗归并后，会损伤场景边界。

因此，项目最终选择保留一版人工认为较合理的：

- `跨模态事件对齐与事件时间线构建/kb_outputs/scene_events.json`

并将其作为稳定输入，进入后续 scene-first 流程。这个决定本身就是方法论上的一个重要结论：

> 对于叙事对齐任务，场景边界一旦经过人工审查被认为合理，应尽量冻结，后续匹配以该场景层为起点，而不是反复重跑底层聚类。

## 6. 知识库规范事件匹配（scene_event → kb_event）

### 6.1 匹配目标

知识库事件层不是为了替代原始事件，而是作为全局标准锚点，用来统一文本和视频对于同一叙事事件的不同命名与不同表达。

### 6.2 知识库节点构造

在代码中，知识库事件会被构造成两种文本表示：

1. `kb_name_repr`
   - 由 `事件名 + event_aliases` 组成
   - 更偏标题级、标签级匹配

2. `kb_detail_repr`
   - 由 `事件名 + aliases + 事件详情 + main_characters + main_locations + timeline_ref` 组成
   - 更偏语义说明级匹配

### 6.3 scene 表示构造

对每个 `scene_event`，构造 `scene_repr_text`，一般由以下内容拼接：

- `scene_name`
- `scene_summary`
- `scene_characters`
- `scene_locations`
- `source_title`

这样，scene 表示兼顾了：

- 标题信息
- 摘要信息
- 人物信息
- 地点信息
- 所属回目 / 集名信息

### 6.4 相似度后端

系统支持两种后端：

1. 若环境中可用 `sentence-transformers`，则优先使用多语种句向量模型：
   - `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`

2. 若不可用，则退化为 TF-IDF：
   - `TfidfVectorizer(analyzer="char_wb", ngram_range=(2,4))`

这保证了算法既可在语义嵌入条件下运行，也可在普通环境下稳定运行。

### 6.5 综合打分函数

对于每个 scene 与每个 kb_event，计算综合匹配分数。其形式为加权线性组合：

\[
Score(scene, kb) = \alpha S_{name} + \beta S_{detail} + \gamma S_{char} + \delta S_{loc} + Bonus(anchor)
\]

其中：

- \(S_{name}\)：scene 与 `kb_name_repr` 的语义相似度
- \(S_{detail}\)：scene 与 `kb_detail_repr` 的语义相似度
- \(S_{char}\)：人物集合 Jaccard 相似度
- \(S_{loc}\)：地点集合 Jaccard 相似度
- `Bonus(anchor)`：若该 KB 事件是 `is_cross_modal_anchor=1`，则给予少量加分

本次 scene-first 实际使用的默认参数记录在：

- `kb_outputs_scene_first/scene_first_run_config.json`

其主要值为：

- `alpha_name = 0.42`
- `beta_detail = 0.23`
- `gamma_char = 0.23`
- `delta_loc = 0.12`
- `top_k_scene_kb = 5`
- `min_scene_kb_score = 0.24`

### 6.6 Top-k 候选与阈值过滤

对每个 scene：

1. 计算与所有 KB 事件的综合分数；
2. 按分数降序排列；
3. 保留 Top-k 候选（如 `top_k_scene_kb=5`）；
4. 若最高分低于阈值，则 scene 不映射到任何 KB；
5. 否则记录：
   - `kb_event_id`
   - `kb_event_name`
   - `kb_top1_score`
   - `kb_topk_candidates`
   - `timeline_id`

### 6.7 匹配结果文件

scene -> kb 的结果输出到：

- `跨模态事件对齐与事件时间线构建/kb_outputs/scene_events_with_kb.json`
- `跨模态事件对齐与事件时间线构建/kb_outputs_scene_first/scene_events_with_kb.json`

其中 scene-first 版本是当前推荐使用的结果。

## 7. scene-first 工作流的形成

在多轮实验后，项目发现已经生成的一版 `scene_events.json` 的切分效果比较理想，而 `unified_events` 和 location 的后续变动不应继续影响这份稳定的场景结果。因此，项目新增了 scene-first 工作流。

### 7.1 入口脚本

当前直接从 scene 开始的脚本为：

- `跨模态事件对齐与事件时间线构建/run_scene_first_matching.py`

### 7.2 scene-first 的核心流程

该流程不再执行“原子事件 → 场景聚类”，而是直接：

1. 读取现成的 `scene_events.json`
2. 构造 `scene_repr_text`
3. 执行 `scene_event -> kb_event`
4. 可选执行 LLM 复核 `scene -> kb`
5. 构造 `kb_event_nodes.json`
6. 构造 `cross_modal_scene_links.json`
7. 可选执行 LLM 复核跨模态链接

### 7.3 为什么 scene-first 很重要

scene-first 的方法论意义在于：

- 将“场景切分”与“场景匹配”解耦；
- 保留人工认可的场景结构；
- 避免底层位置、粒度、归一化策略的变动不断扰动上层对齐结果；
- 使跨模态匹配更可控、更可复现。

## 8. 跨模态场景链接构建（text scene ↔ video scene）

### 8.1 构建原则

跨模态对齐并不是让所有 scene 两两比较，而是先要求文本 scene 和视频 scene 映射到同一个 `kb_event_id`，然后才在该知识库事件内部做链接构建。

因此，跨模态链接的基本前提是：

- `text_scene.kb_event_id == video_scene.kb_event_id`

### 8.2 候选生成

对于每个 `kb_event_id`：

1. 收集所有匹配到它的文本 scenes；
2. 收集所有匹配到它的 视频 scenes；
3. 分别按以下指标排序并截断：
   - `kb_top1_score`
   - `member_count`
   - `start_order`
4. 只保留前若干条（如 `top_k_links_per_kb = 8`）参与组合。

### 8.3 链接打分函数

对于每个文本 scene 与视频 scene 的候选对，计算：

\[
LinkScore = 0.45 S_{textKB} + 0.35 S_{videoKB} + 0.12 J_{char} + 0.08 J_{loc}
\]

其中：

- \(S_{textKB}\)：文本 scene 的知识库匹配分数
- \(S_{videoKB}\)：视频 scene 的知识库匹配分数
- \(J_{char}\)：文本与视频场景人物集合的 Jaccard 相似度
- \(J_{loc}\)：文本与视频场景地点集合的 Jaccard 相似度

只有当综合得分高于阈值（如 `min_cross_modal_score = 0.28`）时，才会生成一条 link。

### 8.4 结果结构

最终生成的链接条目包含：

- `link_id`
- `kb_event_id`
- `event_name`
- `canonical_event_name`
- `alignment_score`
- `alignment_type`
- `relation`
- `text`
- `video`
- `shared`
- `kb_event`
- `llm_review`（若经过 LLM 审查）

其中 `text` 与 `video` 两侧都保留：

- `scene_id`
- `scene_name`
- `scene_summary`
- `source_path`
- `chapter_title` / `episode_title`
- `member_count`
- `members`
- `representative`

这种结构既支持学术分析，也直接支持前端展示。

## 9. LLM 复核机制

规则匹配与相似度打分能够提供较稳定的初筛结果，但仍然会遇到两类问题：

1. 某些 scene 在多个 KB 事件之间边界模糊；
2. 某些 text scene 与 video scene 虽然共享同一规范事件，但实际上只是同一叙事簇中的不同片段，不是同一场景。

因此，项目引入了大语言模型作为**二阶段审查器**。

### 9.1 LLM 复核 1：scene_event → kb_event

#### 复核触发条件

并不是所有 scene 都送入 LLM，而是只对模糊样本复核。典型条件包括：

- `scene_score_low <= kb_top1_score <= scene_score_high`
- top1 与 top2 分数差较小（即 `gap <= scene_gap_threshold`）
- 总复核数量不超过上限（如 `max_scene_items`）

#### Prompt 设计

对每个待复核场景，提供：

- `scene_id`
- `scene_name`
- `scene_summary`
- `scene_characters`
- `scene_locations`
- `source_title`
- Top-k 候选 KB 事件列表

要求模型输出：

- `best_kb_event_id`
- `decision` (`aligned` 或 `unmatched`)
- `confidence`
- `reason`

#### 批处理加速

最初实现为一条一请求，速度较慢。后续优化为：

- 分批复核多个 scene
- 每批大小如 `scene_batch_size = 8`
- 输出批次进度日志

例如：

- 待复核 `43` 条，分 `6` 批

这显著提升了整体运行速度和可观测性。

### 9.2 LLM 复核 2：cross_modal_scene_link

#### 复核目的

即使文本 scene 与视频 scene 映射到同一个 KB 事件，也不一定就属于同一个具体叙事场景。很多误链属于：

- 同一规范事件的不同片段；
- 同一人物线但不同章节；
- 前因、后果、余波被错当成同场景。

因此，需要进一步让 LLM 判断：

> 这两个场景是否真的可以视为同一叙事场景。

#### 输入内容

给模型提供：

- `link_id`
- 文本场景摘要
- 视频场景摘要
- 共享人物
- 共享地点
- 规范事件信息
- 对齐分数

输出：

- `decision` (`aligned` / `unmatched`)
- `confidence`
- `reason`

#### 批处理优化

同样地，cross-modal link 复核也由一条一调升级为：

- 批量复核
- 例如 `link_batch_size = 8`
- 终端显示总批次数和当前进度

### 9.3 LLM 配置

当前运行配置记录在：

- `kb_outputs_scene_first/scene_first_run_config.json`

主要参数包括：

- `model_name = qwen3.6-plus`
- `timeout = 120`
- `max_retries = 3`
- `scene_batch_size = 8`
- `link_batch_size = 8`
- `scene_score_low = 0.24`
- `scene_score_high = 0.72`
- `link_score_low = 0.28`
- `link_score_high = 0.78`
- `accept_if_aligned_conf_ge = 0.70`

这些参数既影响 LLM 复核规模，也影响最终过滤强度。

## 12. 事件时间线构建组件

在完成 `scene_event -> kb_event -> cross_modal_scene_link` 之后，本项目并未停留在“文本场景与视频场景已经对齐”的层面，而是进一步尝试回答一个更具有叙事研究意义的问题：

> 这些跨模态对齐成功的事件，究竟应该被放置到《红楼梦》整体叙事时间轴的什么位置上？

因此，在跨模态对齐层之上，又新增了一个“事件时间线构建组件”。该组件的目标，是把每一个已经完成跨模态对齐的事件链接进一步映射到外置时间标准库上，生成可排序、可聚合、可解释的叙事时间线节点。

### 12.1 输入与目标

该组件的输入包括两部分：

1. **跨模态匹配事件库**
   - `跨模态事件对齐与事件时间线构建/kb_outputs_scene_first/cross_modal_scene_links.json`

2. **外置时间标准库**
   - `知识库/红楼梦时间线.csv`

其中，跨模态匹配事件库中的每一条记录都已经是一个“高质量场景链接对象”，至少包含：

- `link_id`
- `kb_event_id`
- `event_name`
- `canonical_event_name`
- 文本场景摘要 `text.scene_summary`
- 视频场景摘要 `video.scene_summary`
- 共享人物 `shared.characters`
- 共享地点 `shared.locations`

外置时间标准库则包含：

- `红楼年份`
- `季节月份`
- `事件名称`

该组件的输出目标，是为每条跨模态事件链接分配一个标准时间标签，包括：

- `timeline_id`
- `timeline_year`
- `timeline_season`
- `timeline_event_name`
- `timeline_ref`

如果确实无法可靠判断，则保留：

- `不确定`

### 12.2 为什么不能只用规则匹配

时间线构建与普通字符串检索不同。原因在于：

1. 跨模态匹配后的事件对象，往往不是完整的大事件，而是其中一个片段；
2. 文本摘要与视频摘要常常分别强调不同细节；
3. 同一规范事件在时间线上通常只有一个标准条目，但当前场景链接可能只是其前奏、高潮或余波；
4. 有些事件名并不和时间线条目逐字一致，但叙事上明确归属于某个时间节点。

因此，如果仅依赖规则字符串匹配，很容易出现两类错误：

- 候选召回不足，导致明明可判定的事件被归为不确定；
- 片段与标准条目之间无法直接逐字对齐，导致时间落点失败。

这也是为什么本项目最终采用了“规则候选召回 + 红学专家式 LLM 判断 + 人工校订”的三级时间定位框架。

### 12.3 时间线候选召回

在实现层面，首先对每个跨模态事件构造一个融合表示 `link_repr`，其内容综合包括：

- `event_name`
- `canonical_event_name`
- 文本场景摘要
- 视频场景摘要
- 共享人物
- 共享地点

同时，对时间标准库中每个条目构造 `timeline_repr`，包括：

- `timeline_year`
- `timeline_season`
- `timeline_event_name`

随后，计算跨模态事件与时间线条目的候选相似度。当前实现中采用的综合分数形式为：

\[
Score_{timeline}(e,t)=\alpha S_{name}(e,t)+\beta S_{summary}(e,t)+\gamma B_{kb}(e,t)
\]

其中：

- \(S_{name}\)：事件名与时间线事件名之间的相似度
- \(S_{summary}\)：融合摘要与时间线条目表示之间的相似度
- \(B_{kb}\)：若规范事件名或展示事件名与时间线事件名有明显覆盖关系，则给予额外加分

当前默认权重为：

- `alpha_name = 0.45`
- `beta_summary = 0.30`
- `gamma_kb = 0.25`

在工程实现上，本项目最终采用的是：

- 先保留 Top-k 候选（默认 `5` 个），无论分数是否高于强阈值；
- 再区分“强候选”与“弱候选”；
- 只有强候选才可直接作为规则命中结果；
- 弱候选则保留给后续 LLM 复核。

这一点是时间线组件优化中的一个重要经验。项目早期版本曾经直接用阈值过滤候选，导致大量样本的 `candidates` 为空，LLM 虽然能理解事件，但无法从空候选中选择条目，从而被迫输出 `unmatched`。修正后改为“始终保留 Top-k 候选”，显著提高了后续时间确定率。

### 12.4 红学专家式 LLM 时间判定

为了解决“片段归属”“前奏/高潮/余波归并”“事件名不完全一致但叙事位置清晰”等问题，本项目在候选召回之上增加了大语言模型复核层。

这里的大模型并不是一个普通文本分类器，而是在 prompt 中明确被设定为：

- 专业的红楼梦学者
- 版本学研究者
- 叙事时间线标注专家

LLM 判定时，被要求遵循以下原则：

1. 不能只看事件名称字面相似度；
2. 必须综合考虑规范事件名、文本摘要、视频摘要、人物、地点、叙事阶段；
3. 若当前事件是某标准时间事件的前置铺垫、核心片段或直接后续，只要归属明确，也可以判为 aligned；
4. 只能从每个事件自己的候选列表中选择 `timeline_id`，不得编造新的时间节点；
5. 如果候选都不足以支撑可靠判断，才输出 `unmatched`。

在调用方式上，该时间线模块与文本事件抽取模块保持一致，采用 DashScope 的 `MultiModalConversation.call(...)` 接口，便于统一项目内部的大模型调用风格。

### 12.5 人工校订机制

即便经过规则候选召回与 LLM 复核，仍会有少量事件无法稳定落点，或出现“规范事件已知，但标准时间库未单列该条目”的情况。因此，本项目进一步引入了人工校订机制。

具体做法是：

1. 导出仍为 `不确定` 的事件到人工审阅表：
   - `timeline_outputs/uncertain_timeline_events_for_manual_review.csv`

2. 在表中保留：
   - 原始 `link_id`
   - `event_name`
   - `canonical_event_name`
   - 文本/视频场景名与来源标题
   - 前 3 个建议候选时间条目

3. 人工填写：
   - `manual_timeline_id`
   - `manual_timeline_year`
   - `manual_timeline_season`
   - `manual_timeline_event_name`
   - `manual_notes`

4. 再通过回写脚本把人工结果更新回：
   - `matched_events_with_timeline.json`
   - `timeline_event_index.json`

这一机制的意义在于，它把时间线标注流程进一步升级为：

> 自动候选召回 → LLM 语义裁决 → 人工最终校订

对于论文写作而言，这一流程既保证了自动化能力，也保留了学术研究中必要的专家把关环节。

### 12.6 时间线 ID 规范化

在时间线构建后期，项目还发现了一个工程细节问题：由于时间线 CSV 在读取与编号过程中可能受到空行、重复行或导入顺序的影响，部分语义完全相同的时间条目可能被分配到不同的 `timeline_id`，例如：

- `TL054`
- `TL055`

它们虽然 `timeline_id` 不同，但对应的年份、时令与事件名称却完全一致。这会导致最终的 `timeline_event_index.json` 中出现语义重复节点，不利于时间轴聚合与前端展示。

为了解决这一问题，项目增加了“时间线 ID 规范化”步骤：

1. 以原始 `红楼梦时间线.csv` 为准；
2. 按照 `(timeline_year, timeline_season, timeline_event_name)` 三元组建立规范映射；
3. 若不同 `timeline_id` 对应同一三元组，则统一回写为同一个 canonical `timeline_id`；
4. 同步更新：
   - `matched_events_with_timeline.json`
   - `timeline_rule_candidates`
   - `timeline_event_index.json`

经过这一步之后，时间线索引从“按 ID 聚合”提升为“按语义唯一时间节点聚合”，使时间轴结构更规范、更适合论文展示和后续可视化使用。

### 12.8 面向人物与地点功能的数据支撑

为了支撑后续两个功能，即“人物相关事件子图与人物时间线”和“地点相关事件子图与地点时间线”，本项目在时间线构建之后又进一步生成了面向实体索引的派生数据：

- `timeline_outputs/person_event_timeline_index.json`
- `timeline_outputs/location_event_timeline_index.json`

其中，`person_event_timeline_index.json` 以人物为中心组织事件，记录某一人物参与的所有跨模态事件及其时间落点。每个人物节点都包含：

- `entity`
- `entity_type = person`
- `event_count`
- `timeline_span`
- `events`

其中 `events` 中每条记录保留：

- `link_id`
- `kb_event_id`
- `canonical_event_name`
- `timeline_id`
- `timeline_year`
- `timeline_season`
- `timeline_event_name`
- `characters`
- `locations`
- 文本场景摘要
- 视频场景摘要

这使得系统可以直接输出某一人物的相关事件子图，并按照 `timeline_sort` 字段生成该人物的成长轨迹或叙事轨迹。例如，对于林黛玉，系统可以按时间顺序串联其入府、葬花、风雨夕等事件；对于贾宝玉，则可以串联入府初见、宝钗扑蝶关联场景、金钏事件、挨打、晴雯撕扇等叙事节点。

`location_event_timeline_index.json` 则以地点为中心组织事件，记录某一地点承载的所有跨模态事件及其时间落点。每个地点节点同样包含：

- `entity`
- `entity_type = location`
- `event_count`
- `timeline_span`
- `events`

在地点字段较稀疏的情况下，项目没有简单放弃地点索引，而是引入了基于规范事件的地点补全策略。例如：

- `宝钗扑蝶` 补全为 `大观园 / 滴翠亭`
- `黛玉葬花` 补全为 `大观园 / 花冢`
- `风雨夕闷制风雨词` 补全为 `潇湘馆`
- `晴雯撕扇` 与 `勇晴雯病补孔雀裘` 补全为 `怡红院`
- `贾雨村判案` 补全为 `应天府衙`

这种处理使地点时间线不再受限于原始 `shared.locations` 的缺失问题，当前最终结果中缺失地点的事件数已经降为 `0`。因此，该数据不仅支持事件时间线展示，也可以进一步支撑地点维度的叙事空间分析。

从后续功能实现角度看，当前数据已经具备如下支撑能力：

1. **人物相关事件子图**
   - 节点可包括人物、事件、时间线节点、文本场景、视频场景；
   - 边可表示“人物参与事件”“事件发生于时间节点”“事件由文本/视频场景共同支撑”。

2. **人物时间线 / 成长轨迹**
   - 以 `person_event_timeline_index.json` 为输入；
   - 按 `timeline_sort.year_order` 与 `timeline_sort.season_order` 排序；
   - 输出人物在不同叙事阶段参与的关键事件序列。

3. **地点相关事件子图**
   - 节点可包括地点、事件、时间线节点、人物；
   - 边可表示“事件发生于地点”“人物在该地点参与事件”“事件对应文本/视频证据”。

4. **地点时间线**
   - 以 `location_event_timeline_index.json` 为输入；
   - 按时间顺序呈现同一空间中发生的关键事件；
   - 可用于分析大观园、怡红院、潇湘馆等地点的叙事功能变化。

因此，时间线构建组件实际上承担了从“跨模态事件对齐结果”到“人物/地点叙事图谱应用”的桥接作用。它使后续功能不必重新回到原始文本或视频中检索，而是可以直接基于清洗后的结构化事件时间线进行子图抽取和时间序列生成。

## 13. 算法设计的优势与局限

### 13.1 优势

1. **分层结构清晰**
   - 原子事件、场景事件、规范事件、跨模态链接四层解耦；
   - 每层职责明确，便于分析与调试。

2. **兼顾可解释性与鲁棒性**
   - 规则匹配负责提供稳定骨架；
   - LLM 负责处理模糊边界样本；
   - 审计日志保留了中间判断过程。

3. **场景级粒度更适合叙事研究**
   - 不再拘泥于原子动作的一对一对齐；
   - 更贴近文学叙事与影视叙事的真实对应关系。

4. **对前端展示友好**
   - 最终输出中保留了 `event_name`、`scene_summary`、`source_text`、`chapter_title`、`video_source_path`、`timeline_id` 等字段；
   - 可以直接用于构建前端对照视图。

### 13.2 局限

1. **知识库覆盖有限**
   - 当前只有一部分 scene 能映射到规范事件；
   - 非核心情节、大量过渡场景仍无法挂 KB。

2. **地点与人物表达仍会影响结果**
   - 如果 location 归一过粗，会伤害 scene 切分；
   - 如果 aliases 覆盖不足，会影响召回率。

3. **LLM 复核仍有边界问题**
   - 有时会把“同一叙事链中的不同片段”也视作 aligned；
   - 有时虽然 reason 明确写“不匹配”，但由于置信度阈值未达到删除条件，链接仍被保留。

4. **目前偏高精度、低召回**
   - 最终保留下来的跨模态链接不多；
   - 但它们通常质量较高。

## 14. 可用于论文的方法描述模板

如果在论文中描述本方法，可以概括为：

> 本研究提出了一种面向《红楼梦》文本与电视剧改编的四层式跨模态事件对齐框架。首先，将文本与视频中的原始事件统一表示为原子事件层；其次，基于叙事顺序、人物与地点重合度以及语义相似性，将相邻原子事件聚合为场景事件；再次，将场景事件映射到人工构建的规范事件知识库，以获得统一的叙事标签与时间线锚点；最后，在共享规范事件的约束下构造文本场景与视频场景的候选链接，并利用大语言模型对模糊映射与模糊链接进行二阶段审查，从而获得更高精度的跨模态场景对应关系。

如果需要突出算法公式，可以写为：

> 设场景事件为 \(s\)，知识库事件为 \(k\)，则场景到知识库的匹配分数定义为：
>
> \[
> Score(s,k)=\alpha S_{name}(s,k)+\beta S_{detail}(s,k)+\gamma J_{char}(s,k)+\delta J_{loc}(s,k)+Bonus(k)
> \]
>
> 其中 \(S_{name}\) 与 \(S_{detail}\) 分别表示标题级与详情级语义相似度，\(J_{char}\) 与 \(J_{loc}\) 分别表示人物集合与地点集合的 Jaccard 相似度，`Bonus(k)` 表示对跨模态锚点事件的偏置项。
>
> 对于共享同一知识库事件的文本场景 \(s_t\) 与视频场景 \(s_v\)，其跨模态链接分数定义为：
>
> \[
> LinkScore(s_t,s_v)=0.45Score(s_t)+0.35Score(s_v)+0.12J_{char}(s_t,s_v)+0.08J_{loc}(s_t,s_v)
> \]
>
> 当链接分数高于阈值时，生成候选跨模态链接，并由大语言模型对中间置信区间内的链接进行二次判别。

## 15. 当前阶段的总结

本项目已经完成了从数据整理、知识库构建、原子事件统一、场景聚类、规范事件映射，到跨模态链接生成与 LLM 复核的完整链路。尤其是 scene-first 工作流的形成，使得整个系统具备了如下特点：

- 有稳定的场景层输入；
- 有可解释的规范事件中介；
- 有可审计的 LLM 复核机制；
- 有面向前端展示的结构化输出；
- 有可直接写入论文方法部分的算法与参数记录。

从研究方法的角度看，这一工作流的核心价值在于：

1. 它不是简单的相似度匹配，而是一个**分层叙事对齐系统**；
2. 它保留了每一步的中间结果，因此既可计算、又可解释；
3. 它把文学研究中的“规范事件”“叙事场景”“人物—地点约束”等概念转化为了可操作的计算结构；
4. 它通过 `LLM + 规则` 的混合策略，在保证可控性的前提下提高了复杂边界样本的处理能力。

如果后续继续扩展，本项目还可以进一步朝以下方向发展：

- 扩充事件知识库覆盖范围；
- 提升地点知识库粒度设计；
- 区分“同一场景”与“同一事件簇”两类链接；
- 引入更强的中文语义模型；
- 在前端做高质量样本分层展示与人工校订闭环。

总之，当前方案已经形成了一套完整的跨模态叙事事件对齐框架，并具备进一步论文化、系统化和产品化的基础。
