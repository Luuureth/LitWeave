# 《茶经》主题知识在 LitWeave 中的重构方案

## 一、核心判断

当前 LitWeave 是基于《红楼梦》设计的，系统主结构是：

| 原系统 | 作用 |
| --- | --- |
| 事件 | 作为主要浏览对象 |
| 人物 | 作为事件的索引维度 |
| 地点 | 作为事件的索引维度 |

《红楼梦》是叙事文学，所以用“事件、人物、地点”很自然。但《茶经》不是叙事文本，而是知识性文本。如果直接把茶文化中的人物、器物、工艺、概念、典籍、茶类全部并列出来，前端会变得很杂，用户也不容易理解。

因此，《茶经》版本不建议把所有知识类型都做成一级入口，而应保留三栏结构，将系统改造成：

| 《红楼梦》版本 | 《茶经》版本 | 说明 |
| --- | --- | --- |
| 事件 | 知识节点 | 系统的主要浏览对象 |
| 人物 | 主题 | 知识节点的分类入口 |
| 地点 | 地域 | 茶产地、水源、地理信息入口 |

也就是说，《茶经》版 LitWeave 的主结构应是：

> 知识节点 + 主题索引 + 地域索引

这是最清晰、最容易落地，也最接近现有系统的数据结构和前端页面的方案。

## 二、三个前端入口如何对应

### 1. “事件”页面改为“知识节点”页面

这是系统最核心的页面。

原来《红楼梦》的事件页面展示的是一个个文学事件，例如“贾雨村判案”“黛玉葬花”。《茶经》版本中，应展示一个个茶知识节点，例如：

- 茶的起源
- 茶树形态
- 采茶方法
- 制茶流程
- 风炉的用途
- 煮茶用水
- 煎茶步骤
- 茶汤品评
- 唐代饮茶方式

每个知识节点相当于原系统中的一个 `event`。

对应关系如下：

| 现有字段 | 《茶经》含义 |
| --- | --- |
| `display_event_id` | 知识节点 ID |
| `event_name` | 知识点名称 |
| `canonical_event_name` | 标准知识点名称 |
| `summary` | 知识点解释 |
| `timeline_year` | 所属篇章 |
| `timeline_season` | 篇章内顺序 |
| `representative_text_json` | 代表性原文证据 |
| `all_text_scenes_json` | 所有相关原文句子 |

前端展示时，原来的“事件卡片”可以改成“知识卡片”。

卡片建议显示：

- 知识点名称
- 所属主题
- 所属篇章
- 简短解释
- 相关地域，如果有
- 原文证据数量

### 2. “人物”页面改为“主题”页面

《茶经》里人物不是主线。真正适合作为索引入口的是“主题”。

主题不宜太多，建议先固定为 6 个一级主题：

| 主题 | 覆盖内容 |
| --- | --- |
| 茶之源 | 茶的起源、茶树、茶叶基本认识 |
| 茶之具 | 茶具、器物、工具 |
| 茶之造 | 采茶、制茶、藏茶 |
| 茶之煮 | 水、火、煮茶、饮茶方法 |
| 茶之品 | 茶汤、味道、品评标准 |
| 茶之史 | 人物、典籍、时代背景、文化影响 |

这 6 个主题足够覆盖大多数茶知识，同时又不会让前端结构变得复杂。

在数据库中，可以暂时复用 `characters` 表和 `display_event_character_relations` 表，但语义改为“主题”。

对应关系如下：

| 现有字段/页面 | 《茶经》含义 |
| --- | --- |
| `characters` | 主题 |
| `character.name` | 主题名称 |
| `/characters` | `/themes`，主题列表页 |
| `/characters/:name` | 某一主题下的知识节点 |

例如：

- “茶之具”主题下包含：风炉、鍑、碾、罗、瓢、盏。
- “茶之煮”主题下包含：择水、候汤、火候、煎茶法。
- “茶之造”主题下包含：采茶、蒸茶、焙茶、藏茶。

这样前端仍然只有一个清晰入口：主题。

### 3. “地点”页面改为“地域”页面

《茶经》涉及很多地理信息，例如茶产地、水源、州郡、山川。它们适合继续使用“地点”入口。

“地域”页面可以包括：

- 茶产地
- 水源地
- 州郡地名
- 山川地名
- 与茶品相关的地理区域

对应关系如下：

| 现有字段/页面 | 《茶经》含义 |
| --- | --- |
| `locations` | 地域 |
| `location.name` | 地名、水名、产区名 |
| `/locations` | 地域列表页 |
| `/locations/:name` | 某地域关联的知识节点 |

例如：

- 峡州
- 越州
- 扬子江
- 中泠泉
- 顾渚山

地域页面的价值是帮助用户从“空间分布”角度理解茶文化。

## 三、哪些信息作为主结构，哪些只作为详情信息

为了避免系统变乱，需要明确区分“一级结构”和“详情信息”。

### 一级结构

只保留三个：

1. 知识节点
2. 主题
3. 地域

### 详情信息

以下内容不要都做成一级页面，只放在知识节点详情页中：

- 人物
- 器物
- 工艺步骤
- 古代术语
- 典籍
- 朝代
- 茶类
- 文化概念

这些内容可以作为标签、关键词、高亮词或补充解释出现。

例如，“风炉的用途”这个知识节点详情页中可以显示：

- 所属主题：茶之具
- 相关地域：无
- 关键词：风炉、煮茶、火候
- 原文证据：《茶经·四之器》相关句子
- 解释：风炉是唐代煮茶时使用的核心器具
- 扩展资料：风炉结构图、现代复原图

这样既保留了知识丰富度，又不会破坏系统结构。

## 四、前端页面建议

### 1. 首页

首页不再强调“多模态叙事事件”，而改为“茶文化知识重构”。

首页三个入口建议为：

| 页面入口 | 原页面 | 新名称 |
| --- | --- | --- |
| `/events` | 事件 | 知识 |
| `/characters` | 人物 | 主题 |
| `/locations` | 地点 | 地域 |

首页统计项建议改为：

- 知识节点数
- 主题数
- 地域数
- 原文证据数
- 扩展资料数

### 2. 知识列表页

原“事件列表页”改为“知识列表页”。

建议按《茶经》篇章顺序分组，而不是按时间线分组。

分组可以是：

- 一之源
- 二之具
- 三之造
- 四之器
- 五之煮
- 六之饮
- 七之事
- 八之出
- 九之略
- 十之图

每个知识卡片显示：

- 知识点名称
- 所属主题
- 所属篇章
- 摘要
- 相关地域

### 3. 主题页

原“人物页”改为“主题页”。

主题页展示 6 个一级主题：

- 茶之源
- 茶之具
- 茶之造
- 茶之煮
- 茶之品
- 茶之史

点击某个主题后，进入该主题下的知识节点列表。

例如点击“茶之具”，展示：

- 风炉
- 鍑
- 碾
- 罗
- 瓢
- 盏

### 4. 地域页

原“地点页”改为“地域页”。

地域页展示茶产地、水源地、州郡和山川。

点击某个地域后，展示与该地域相关的知识节点。

例如点击“峡州”，可以展示：

- 峡州茶产地记载
- 唐代茶区分布
- 《茶经》中关于峡州的原文证据

### 5. 知识详情页

原“事件详情页”改为“知识详情页”。

页面结构建议为：

1. 知识点名称
2. 所属主题
3. 所属篇章
4. 相关地域
5. 知识点解释
6. 原文证据
7. 白话释义
8. 相关关键词
9. 扩展资料

原来的“文本证据 + 视频证据”结构可以改为：

| 原结构 | 新结构 |
| --- | --- |
| 文本证据 | 原文证据 |
| 视频证据 | 扩展资料 |

扩展资料可以是：

- 器物图片
- 工艺流程图
- 地图
- 茶艺视频
- 复原图

## 五、数据结构建议

每个知识节点建议整理为如下结构：

```json
{
  "knowledge_id": "TEA_K001",
  "name": "风炉的用途",
  "canonical_name": "风炉",
  "summary": "风炉是唐代煮茶使用的重要器具，主要用于生火煮水，是《茶经》中茶具系统的重要组成部分。",
  "theme": "茶之具",
  "chapter": "四之器",
  "chapter_order": 4,
  "item_order": 12,
  "regions": [],
  "keywords": ["风炉", "煮茶", "火候"],
  "evidence": [
    {
      "page": 23,
      "sentence_id": 5,
      "source_text": "原文句子",
      "translation": "白话释义",
      "source_path": "原始文件路径"
    }
  ],
  "extended_materials": [
    {
      "type": "image",
      "title": "风炉结构示意图",
      "path": "图片路径"
    }
  ]
}
```

如果复用现有 LitWeave 数据表，可以映射为：

| 知识节点字段 | 现有字段 |
| --- | --- |
| `knowledge_id` | `display_event_id` |
| `name` | `event_name` |
| `canonical_name` | `canonical_event_name` |
| `summary` | `summary` |
| `theme` | `event_characters_json` |
| `chapter` | `timeline_year` |
| `item_order` | `timeline_sort_season` |
| `regions` | `event_locations_json` |
| `evidence` | `all_text_scenes_json` |
| `extended_materials` | `all_video_scenes_json` 或新增字段 |

## 六、检索逻辑建议

为了保持清晰，检索逻辑只分三层：

### 1. 全文检索

搜索范围：

- 知识点名称
- 摘要
- 原文句子
- 白话释义
- 关键词

用户可以搜索：

- 风炉
- 煎茶
- 陆羽
- 中泠泉
- 火候

### 2. 主题筛选

用户从 6 个主题中筛选知识节点：

- 茶之源
- 茶之具
- 茶之造
- 茶之煮
- 茶之品
- 茶之史

### 3. 地域筛选

用户根据地域筛选知识节点：

- 茶产地
- 水源地
- 州郡
- 山川

这三层已经可以覆盖主要使用场景，不需要一开始就做复杂知识图谱。

## 七、与原系统的关系

改造后的系统不是完全推翻原系统，而是做语义替换。

原系统逻辑：

> 事件是中心，人物和地点用于索引事件。

《茶经》系统逻辑：

> 知识节点是中心，主题和地域用于索引知识节点。

对应关系非常明确：

```text
红楼梦：事件 -> 人物 -> 地点
茶经：  知识 -> 主题 -> 地域
```

这也是向老师汇报时最应该强调的核心设计。

## 八、实施步骤

### 第一步：修正数据编码

当前 `sentence_knowledge_v2.json` 存在编码错位问题，需要先修正，否则无法稳定导入。

### 第二步：从句子中生成知识节点

不要让每个句子都直接成为一个节点，而应把相同或相近的知识点合并。

例如多句话都提到“风炉”，最终合并成一个知识节点：

> 风炉的用途

### 第三步：给每个知识节点分配主题

每个知识节点只分配 1 个主主题，必要时可以有辅助关键词。

例如：

| 知识节点 | 主主题 |
| --- | --- |
| 茶树形态 | 茶之源 |
| 风炉 | 茶之具 |
| 采茶方法 | 茶之造 |
| 煮茶用水 | 茶之煮 |
| 茶汤品评 | 茶之品 |
| 陆羽与《茶经》 | 茶之史 |

### 第四步：提取地域信息

只有真正涉及地名、水名、产区的知识节点才关联地域。

没有地域信息的知识节点不必强行填写。

### 第五步：改前端文案和页面语义

优先改名称，不急于大规模改结构。

需要修改：

- 事件 -> 知识
- 人物 -> 主题
- 地点 -> 地域
- 事件概要 -> 知识解释
- 文本证据 -> 原文证据
- 视频证据 -> 扩展资料

### 第六步：再考虑扩展知识图谱

等三栏结构稳定后，再考虑增加更复杂的关系，例如：

- 器物和用途
- 工艺步骤顺序
- 人物和典籍
- 茶产地和茶品

这些可以作为第二阶段工作，不建议一开始就放进主系统结构。

## 九、汇报时的表达方式

可以这样向老师说明：

> 原来的 LitWeave 以《红楼梦》为对象，适合用“事件-人物-地点”组织叙事知识。但《茶经》是知识性文本，没有连续叙事事件，因此我们将系统中心从“事件”调整为“知识节点”，再用“主题”和“地域”作为两个主要索引维度。这样既保留了原系统的三栏结构，又更符合茶文化知识的组织方式。

简化后的设计是：

```text
原系统：《红楼梦》 = 事件 + 人物 + 地点
新系统：《茶经》 = 知识节点 + 主题 + 地域
```

这个方案的优点是：

1. 结构清晰，前端入口不混乱。
2. 复用现有 LitWeave 页面和数据库成本低。
3. 符合《茶经》作为知识性文本的特点。
4. 原文证据仍然可以完整保留。
5. 后续可以逐步扩展器物、工艺、人物、典籍等更细关系。

## 十、结论

《茶经》主题知识重构不应把所有茶文化信息都做成并列入口，而应先建立一个稳定、清晰的主结构。

推荐方案是：

> 知识节点为中心，主题和地域作为索引。

前端只保留三个主要入口：

- 知识
- 主题
- 地域

人物、器物、工艺、术语、典籍等内容放在知识详情页中，以标签、关键词、解释和扩展资料的形式呈现。

这样既能适配现有 LitWeave 系统，又能避免茶文化知识体系过于庞杂，比较适合当前阶段向老师汇报和后续落地实现。
