# 红楼梦多模态知识内容理解（方法 + 实验）处理文档

> 面向项目实现的工程文档。内容基于当前代码：`红楼梦文本/deal_txt.py`、`剧版红楼梦/deal_video.py` 及知识库归一化流水线脚本整理。

---

## 1. 任务定义与总体架构

本项目的“多模态知识内容理解”目标是：将《红楼梦》文本章节与剧版视频片段统一转为**可计算的叙事事件结构**，并进一步归一人物/地点，为后续知识图谱、时间线、人物关系网络提供稳定输入。

结合你给的架构图，工程上对应三层：

1. **输入与预处理层**
   - 视频模态：原始剧集 -> 粗粒度分段 -> 视频片段（`*.mp4`）。
   - 文本模态：原始章节文本 ->（必要时）章节级切分 -> 文本片段（`*.txt`）。
2. **多模态知识理解层**
   - 统一提示词框架驱动 LLM，执行叙事事件切分与事件属性抽取。
3. **统一事件表示层**
   - 输出统一 JSON 事件结构：`action`、`characters`、`location`、`time_hint`、`explicit_time`、`relation_to_previous`、`event_summary`（文本侧额外保留 `source_text`）。

## 2. 输入与预处理层（对应代码实现）

## 2.1 文本模态预处理

### 2.1.1 输入来源
- 目录：`红楼梦文本/hongloumeng_txt/第XXX回.txt`
- 基本元信息读取：`chapter_id`、`chapter_title`、正文 `body`

### 2.1.2 长文本分段策略（失败章节重处理）
- 脚本：`红楼梦文本/split_failed_chapters.py`
- 核心算法：
  1. 将正文按空行归并为“段落”；
  2. 在接近总字数 50% 的位置寻找切分点；
  3. 评分函数 = 距离中点惩罚 - 边界质量奖励；
  4. 边界质量由句末标点、下段开头叙事词（如“且说”“次日”）和短段惩罚共同决定；
  5. 约束两侧至少各占 30%，避免极端不均匀切分。

这是一种**启发式最优切分（heuristic split point search）**，目标是兼顾 token 长度与叙事边界自然性。

### 2.1.3 文本处理入口与重试机制
- 主脚本：`红楼梦文本/deal_txt.py`
- 关键工程策略：
  - 支持按章节区间处理（`CHAPTER_START/END`）；
  - 支持从历史失败 JSON 自动回收目标章节（`TARGET_FROM_FAILED_JSON`）；
  - 支持优先读取 `_1/_2` 分段文本并合并输出（`PREFER_SPLIT_PARTS`）；
  - 支持指数退避重试（最多 `MAX_RETRIES`）；
  - 输出 `.raw.txt` 保存模型原始响应，便于审计与错误追溯。

---

## 2.2 视频模态预处理

### 2.2.1 输入来源
- 目录：`剧版红楼梦/hongloumeng_segments/hongloumengX_segments/N.mp4`
- 路径驱动的 episode/segment 推断：
  - `segment_id` 由文件名数字映射为 `Sxx`
  - 输出路径自动映射到 `hongloumeng_json/hongloumengX_json/N.json`

### 2.2.2 重跑策略
- 主脚本：`剧版红楼梦/deal_video.py`
- 当前采用**定向重跑清单** `REPROCESS_VIDEO_PATHS`，针对问题片段精准覆盖输出，避免全量重算。

### 2.2.3 视频调用形式
- 使用 DashScope `MultiModalConversation.call`
- 单轮 message 中同时提交：
  - `{"video": "file://..."}`
  - `{"text": prompt}`
- 失败重试 3 次（指数等待）
- 解析后强制同步 `event_count == len(events)`

## 3. 多模态知识理解层：统一事件抽取方法

## 3.1 抽取目标

无论文本或视频，都围绕“叙事事件单元”抽取：
- **动作核心**：`action`
- **事件参与者**：`characters`
- **主地点锚点**：`location`（只能一个）
- **时间线属性**：`time_hint`、`explicit_time`、`relation_to_previous`
- **摘要**：`event_summary`
- 文本侧额外要求证据片段：`source_text`

## 3.2 事件切分原则（跨模态一致）

提示词中明确统一原则：
1. 按“叙事事件”切，不按自然段/镜头机械切；
2. 连续表达同一事件不拆；
3. 同一段出现明显两件事可拆；
4. 不为凑数量强拆。

本质是把原始序列（文字流、镜头流）映射为**语义事件序列**，属于“LLM 驱动的事件分段 + 槽位填充”范式。

---

## 4. 统一事件表示层（JSON Schema 与后处理）

## 4.1 统一事件 JSON

项目统一落到结构化 JSON，核心字段：
- `event_id`（E01, E02...）
- `narrative_order`
- `action`
- `characters`（数组）
- `location`
- `time_hint`（`null/background/same_time/after/flashback`）
- `explicit_time`
- `relation_to_previous`（`start/sequential/flashback/parallel/unclear`）
- `event_summary`

文本侧额外字段：
- `source_text`（必须为原文连续摘录，不可改写）

## 4.2 稳定化后处理

`deal_txt.py` 中对模型输出执行标准化：
1. 去除代码块包裹并解析 JSON；
2. 统一补齐缺失字段（如 `source_text`）；
3. 重建 `event_id` 与 `narrative_order`；
4. 若非首事件却出现 `relation_to_previous="start"`，自动修正为 `sequential`。

这一步保证“模型输出可变”到“下游消费稳定”之间的接口一致性。

## 5. 提示词工程设计（核心）

## 5.1 设计目标

你的提示词不是“自由生成”，而是**任务约束型提示词（task-constrained prompt）**，目标是提高结构化可用性，而非文学解释性。

## 5.2 文本侧提示词策略（`deal_txt.py`）

1. **任务对齐**：先声明最终用途（知识图谱/时间线/人物网），让模型优化信息粒度；
2. **字段级硬约束**：
   - 枚举值限制（`time_hint`、`relation_to_previous`）；
   - 单地点约束（`location` 只能一个）；
   - 不确定即 `null`；
3. **证据绑定**：
   - 强制 `source_text` 必须摘录原文，禁止改写；
4. **格式强约束**：
   - 只输出合法 JSON，不要解释；
   - 明确禁止中文引号/中文布尔值；
5. **叙事逻辑约束**：
   - 背景、插叙、并行等关系有明确规则，降低时间线噪声。

## 5.3 视频侧提示词策略（`deal_video.py`）

1. **镜头->事件去耦**：明确“按叙事事件切分，不按镜头切”；
2. **噪声抑制**：片头、片尾、风景过场无叙事功能时不输出事件；
3. **语言约束**：
   - `action/characters/location/event_summary` 必须简体中文；
   - 禁止英文人名与英文句子；
4. **时间来源限制**：
   - `explicit_time` 仅可来自对白/旁白/字幕/画面可读时间信息。

## 5.4 归一化阶段提示词策略（人物/地点）

### 人物归一（`normalize_character_mentions_llm.py`）
- 闭集映射：`canonical_name` 只能来自人物表 `姓名` 或 `unknown`；
- 高歧义称谓（如“二爷”）优先 `unknown`；
- 输出按输入顺序一一对应，防止错位。

### 地点归一（`normalize_location_mentions_llm.py`）
- 闭集映射：`canonical_location` 只能是标准地点或 `unknown/generic`；
- 强调“层级包含”语义：房中/内室映射到可点击上层节点（如“潇湘馆”“怡红院”）；
- 泛称（园中、厅上、厨房）要求输出 `generic`。

## 6. 核心算法清单（按流程）

1. **启发式章节切分算法**（文本过长处理）  
   - 目标长度约束 + 边界质量打分 + 全局最优切点选择。

2. **事件抽取与模式对齐算法**（LLM 约束抽取）  
   - 叙事事件切分 + 固定槽位填充 + 枚举值限制。

3. **规则优先分类算法（人物/地点）**  
   - 关键词/正则/精确匹配构成 decision list；  
   - 仅将高不确定类型送入 LLM，降低错误与成本。

4. **闭集归一算法（LLM + 校验）**  
   - 候选集合注入 prompt；  
   - 输出集合成员校验（非法值直接报错）；  
   - mention 回写以输入为准，防止模型轻微改写造成链路断裂。

5. **分批处理与断点容错**  
   - 批处理（character 默认 45，location 默认 40）；  
   - partial 文件 + raw log 保证失败可恢复。

6. **知识库聚合算法**  
   - mention map（全量映射，包括 unknown/generic）  
   - canonical KB（仅保留稳定节点）  
   - 聚合别名、来源、频次与父级关系。

## 7. 方法实验设计（Method + Experiment）

## 7.1 实验目标

验证三件事：
1. 文本/视频是否能稳定抽取为统一事件 JSON；
2. 人物/地点归一是否能显著降低别称碎片；
3. 产物是否可直接支撑“按人物/地点聚合事件”。

## 7.2 实验流程（可复现）

### A. 多模态事件抽取
- 文本：运行 `红楼梦文本/deal_txt.py`
- 视频：运行 `剧版红楼梦/deal_video.py`

### B. Mention 聚合
- 人物：`scripts/extract_characters_to_csv.py`
- 地点：`extract_locations_to_csv.py`

### C. 归一化流水线
- 人物：
  1) `知识库/character_normalization_pipeline.py`
  2) `知识库/normalize_character_mentions_llm.py`
  3) （可选）`知识库/enrich_character_table_from_llm_unknowns.py`
  4) `知识库/build_character_kb_from_normalization.py`
- 地点：
  1) `知识库/location_normalization_pipeline.py`
  2) `知识库/normalize_location_mentions_llm.py`

## 8. 误差与鲁棒性分析

## 8.1 主要误差来源

1. **模型格式误差**：返回非严格 JSON（已通过 `try_parse_json` + 校验缓解）；
2. **长输入不稳定**：超长章节或超大批次更易引发解析失败（已引入分段与批处理）；
3. **歧义称谓**：如“太太”“二爷”上下文不足时归一不确定；
4. **表不完备**：真实人物不在标准表时会被压成 `unknown`（通过增补脚本闭环解决）。

## 8.2 现有鲁棒性机制

- 指数退避重试；
- 失败样本重跑机制（按章节/按视频片段）；
- partial 中间结果落盘；
- raw 文本全量审计；
- 结果字段与闭集合法性校验；
- 输入输出长度一致性检查（防错位）。

---

## 9. 如何把结果用于知识图谱与时间线

1. 以事件 JSON 为基础边（事件节点）；
2. 用 `characters` 和人物 `character_kb.json` 做实体对齐；
3. 用 `location_mention_map.json` 将事件地点替换为 `resolved_location`；
4. 对 `generic/unknown` 可在前端默认隐藏，避免噪声节点；
5. `time_hint + relation_to_previous + narrative_order` 组合形成章节/片段内部时间线。

---

## 10. 可继续优化的方向

1. 增加“解析失败自动降批重试”策略（当前主要依赖人工重跑）；
2. 增加人物/地点低置信样本自动导出人工复核清单；
3. 引入跨模态对齐约束（同章节文本与对应视频片段的事件一致性检查）；
4. 在 `event_summary` 上增加信息密度控制（避免过短或模板化）。
