# 红楼梦地点归一化全流程说明

## 1. 背景与目标

本项目的地点归一化与人物归一化不同，不是“标准名-别称”的平级映射，而是“**层级地点归并**”：

- 人物场景里出现的“黛玉房中”“宝玉卧室”“宁国府抱厦”等，通常是更细粒度空间；
- 标准库（`红楼梦地点表.csv`）需要保留的是可点击、可聚合事件的稳定节点（如 `潇湘馆`、`怡红院`、`荣国府`）；
- “园中/厅上/厨房/书房”等泛称不适合做前端点击节点，应标记为 `generic` 或 `unknown`，并从最终地点节点库中剔除。

目标产物有两个：

1. **地点标准节点库**：供前端“点击地点看事件”。
2. **mention 归一映射表**：供事件数据把原始地点替换成标准地点，同时保留来源可追踪。

---

## 2. 输入数据与标准数据

## 2.1 标准地点表（闭集）

文件：`知识库/红楼梦地点表.csv`

核心字段：

- `standard_location`：标准地点名（唯一映射目标集合）
- `parent_location`：父级地点（表达层级包含关系）
- `location_type`：府邸/院落/园林等类型
- `note`：人工注释

其中 `standard_location` 构成模型可选的“闭集”，模型不得输出集合外具体地点名。

## 2.2 原始地点来源（事件 JSON）

数据来自两类事件抽取 JSON：

- 文本：`红楼梦文本/hongloumeng_txt_json/*.json`
- 视频：`剧版红楼梦/hongloumeng_json/*.json`

读取字段：`events[].location`。

---

## 3. 全流程总览（四阶段）

按顺序执行：

1. `extract_locations_to_csv.py`
2. `知识库/location_normalization_pipeline.py`
3. `知识库/normalize_location_mentions_llm.py`
4. `知识库/build_location_kb.py`

---

## 4. 阶段一：地点抽取与溯源聚合

脚本：`extract_locations_to_csv.py`

## 4.1 方法

- 遍历两类 JSON（文本/视频）；
- 抽取每个事件的 `location` 字符串；
- 统计两层粒度：
  - 按 `(location, source)` 聚合统计；
  - 按 `(location, source, json_path)` 文件级明细统计。

## 4.2 生成文件

1. `all_locations.csv`（聚合表）  
字段：
- `location`
- `source`（`txt` / `video`）
- `occurrence_count`（总出现次数）
- `file_count`（出现于多少 JSON）
- `json_paths`（`|` 拼接的 JSON 路径列表）

2. `all_locations_by_file.csv`（文件级明细）  
字段：
- `location`
- `source`
- `json_path`
- `occurrence_count`（该地点在该 JSON 内出现次数）

## 4.3 算法要点

- 使用 `Counter` 统计单文件内出现次数；
- 使用 `defaultdict(int)` 聚合全局计数；
- 使用 `defaultdict(set)` 聚合去重文件列表；
- 这样既支持全局频次，也保留可追溯源文件粒度。

---

## 5. 阶段二：规则预分类与 LLM 任务构造

脚本：`知识库/location_normalization_pipeline.py`

## 5.1 核心思想：规则优先，模型补充

先用规则把易判定项分类，减少模型负担并提升一致性：

- `canonical`：与标准地点完全一致；
- `generic`：泛称/方位/功能室通称；
- `descriptive`：人物+房中/内室类描述；
- `subspace`：标准大地点下的局部空间；
- `alias`：简称/别写/其余待判定项。

其中仅 `alias/descriptive/subspace` 进入 LLM。

## 5.2 规则体系（当前实现）

1. **精确泛称白名单** `GENERIC_EXACT`  
例如：`园中`、`厅上`、`外厅`、`厨房`、`书房`、`院中`、`路上` 等。

2. **泛称正则** `GENERIC_PATTERN`  
补充整词匹配：`夹道`、`甬道`、`回廊`、`帘外` 等。

3. **人物居室描述正则** `DESCRIPTIVE_PERSON`  
匹配“人物名 + 房中/房内/内室/住处/上房”等。

4. **子空间识别**  
- 前缀命中：`荣国府*`、`宁国府*`、`大观园*` 等；
- 后缀命中：`抱厦`、`暖阁`、`内院`、`桥边` 等局部空间词。

5. **别称提示** `ALIAS_HINT_EXACT`  
如：`荣府 -> 荣国府`、`宁府 -> 宁国府`、`蘅芜苑 -> 蘅芜院`（仅提示，最终仍由闭集决策）。

## 5.3 输出中间结果

1. `location_pipeline_out/locations_classified.csv`  
每条地点带上：
- `location_type`
- `rule_note`
- `json_paths`

2. `location_pipeline_out/location_classification_stats.json`  
记录各类型数量，便于监控规则效果。

3. `location_pipeline_out/llm_location_normalization_input.json`  
供 LLM 消费，包含：
- `candidate_canonical_locations`（闭集）
- `standard_table_rows`（含 `parent_location` 的层级表）
- `items`（待归一明细，含 source、频次、json_paths、rule_note）

## 6. 阶段三：LLM 批处理归一化

脚本：`知识库/normalize_location_mentions_llm.py`

## 6.1 模型调用策略

- 调用方式与 `deal_txt.py` 一致（DashScope + `MultiModalConversation.call`）；
- API Key 优先级：
  1) 环境变量 `DASHSCOPE_API_KEY`
  2) 回退读取 `红楼梦文本/deal_txt.py` 中 `API_KEY`；
- 批大小默认 `40`（可配置 `LOCATION_NORM_BATCH_SIZE`）。

## 6.2 提示词方法

提示词明确约束：

- 映射目标只能是：
  - 标准闭集地点；
  - `unknown`；
  - `generic`；
- 明确“层级包含”语义（人物房间 -> 上级标准院落）；
- 使用 `standard_table_rows` 让模型看到 `parent_location` 层级信息；
- 输出必须是严格 JSON，且 `results[i]` 与输入第 `i` 条一一对应。

## 6.3 校验与鲁棒性

脚本中做了强约束验证：

- 结果条数必须与批次输入一致；
- `confidence` 必须在 `high/medium/low`；
- `canonical_location` 必须在闭集或 `unknown/generic`；
- 若模型回显 `mention` 与输入不一致，以输入值覆盖，防止细微改写导致后续链路断裂。

并且每批写入：

- `location_normalization_llm.partial.json`（断点恢复/中间态）
- `location_normalization_llm.raw.txt`（原始响应审计）

## 6.4 常见失败模式（你遇到的 JSONDecodeError）

错误表现：`json.decoder.JSONDecodeError`。  
常见原因：

- 模型返回了非严格 JSON（缺冒号、尾逗号、多余文字）；
- 响应太长导致格式破损；
- 单批输入内容过大，模型输出稳定性下降。

建议处理：

1. 降低批大小：`LOCATION_NORM_BATCH_SIZE=20` 或 `25`；
2. 增加重试逻辑（解析失败时二次请求，仅重跑失败批次）；
3. 在 `try_parse_json` 前增加“提取首个 JSON 对象”容错；
4. 保留 raw log，失败后可人工检查具体批次响应。

## 7. 阶段四：合并为可用知识库

脚本：`知识库/build_location_kb.py`

## 7.1 合并规则

输入：

- `locations_classified.csv`
- `llm_location_normalization_input.json`
- `location_normalization_llm.json`（若存在且条数匹配）

逐条生成 `resolved_location`：

- `location_type == canonical` -> 直接用原值；
- `location_type == generic` -> `generic`；
- 其余 -> 使用 LLM 结果；缺失则 `unknown`。

## 7.2 输出文件

1. `location_pipeline_out/location_kb.json`  
仅收录可用标准节点（排除 `generic/unknown`），每个节点包含：
- `canonical_location`
- `aliases`（归并别名）
- `sources`
- `parent_location`
- `occurrence_total`

2. `location_pipeline_out/location_mention_map.json`  
保留全量映射行（包括 `generic/unknown`），每条含：
- `original_location`
- `source`
- `json_paths`
- `resolved_location`
- `llm_confidence` / `llm_reason`（若有）

## 7.3 一致性保护

若 LLM 输入与输出条数不一致（例如你改了输入但还在用旧输出）：

- 脚本会打印警告；
- 自动忽略旧 LLM 结果并继续产出（LLM 部分视作 `unknown`）；
- 防止流程直接崩溃。

---

## 8. 关键算法与方法总结

本流程使用的是“**规则系统 + 闭集约束 LLM + 可审计合并**”的混合范式：

1. **规则分类（Rule-based Classification）**  
通过词表与正则把容易确定的样本提前分流，减少模型不确定性。

2. **层级语义归并（Hierarchical Normalization）**  
把“房间/内室/局部空间”映射到可交互的上级标准节点。

3. **闭集判定（Closed-set Mapping）**  
模型只能从 `standard_location` 列表中选择，避免幻觉地点。

4. **批处理 + 严格校验（Batch + Validation）**  
逐批调用，逐批校验格式与字段合法性，保证输出可机读。

5. **溯源链路（Data Lineage）**  
通过 `json_paths` 和 `all_locations_by_file.csv` 保留“地点 -> 原始 JSON”关联能力。

6. **双产物设计（Node KB + Mention Map）**  
- `location_kb.json`：面向前端地点导航；
- `location_mention_map.json`：面向事件替换与来源追踪。

## 9. 执行命令（推荐）

```bash
python "scripts/extract_locations_to_csv.py"
python "知识库/location_normalization_pipeline.py"
python "知识库/normalize_location_mentions_llm.py"
python "知识库/build_location_kb.py"
```

如果 LLM 容易报 JSON 解析错误，可先降批大小：

```bash
set LOCATION_NORM_BATCH_SIZE=20

```

## 10. 结果如何用于“点击地点看事件”

推荐在事件展示层执行以下逻辑：

1. 对每个事件读取原始 `event.location`；
2. 根据 `(original_location, source)` 在 `location_mention_map.json` 查 `resolved_location`；
3. 若 `resolved_location` 是标准地点，则归入该地点时间线；
4. 若为 `generic/unknown`，可：
   - 不在地点导航中显示；
   - 仅在检索模式下保留原文地点字符串。

这样既保证前端地点节点稳定、可解释，又保留原始数据可追溯性。
