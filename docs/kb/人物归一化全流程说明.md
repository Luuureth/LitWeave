# 《红楼梦》人物 Mention 归一化全流程说明

本文档系统梳理项目中「从事件 JSON 抽取人物 mention → 规则预处理 → 大模型辅助映射 → 人物表增补 → 最终人物知识库」的完整流水线，说明各阶段所用方法、算法逻辑与产物，便于复现、审计与迭代。

---

## 一、目标与约束

### 1.1 核心目标

- 将文本侧（`hongloumeng_txt_json`）与剧版侧（`hongloumeng_json`）事件数据中的 **`characters` 字段**里出现的各类 **mention**（标准名、简称、别称、关系称呼、泛称、视觉描述等）进行 **清洗、分类与归一**。
- 以 **标准人物表**（`红楼梦人物表.csv`）中的 **`姓名`** 为主键集合，尽量将可确定的别称映射到标准名。
- 承认 **人物表不完备**：对无法映射但属于原著可立条的人物，通过 **二次大模型判别** 增补至人物表。
- **不**将明显泛称、群体称呼、纯视觉噪声强行绑定到某一标准人物。
- 最终产出 **结构化人物知识库**（`character_kb.json`）：标准名 + 别称列表 + 来源与说明，供知识图谱与后续检索使用。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| 半自动 | 规则可解释 + 大模型补洞 + **人工抽查**最终权威 |
| 不虚构标准名 | 首次 LLM 映射仅允许输出人物表已有 `姓名` 或 `unknown` |
| 分层处理 | 先规则减噪，再 LLM，再对 unknown 分流（补表 vs 保持 unknown） |
| 可追溯 | 各阶段保留 CSV/JSON/原始模型输出（`.raw.txt`） |

## 三、阶段划分与逻辑顺序

整体顺序为 **单向流水线**，后一阶段依赖前一阶段的输出（或更新后的标准表）。

```
事件 JSON
    → [统计与汇总]
    → [规则分类]
    → [首次 LLM 归一]
    → [二次 LLM 人物表增补]（可选，针对 unknown / 表不完备）
    → [聚合为 character_kb.json]
```

## 四、阶段 A：Mention 抽取与统计

### 4.1 方法

- **输入**：上述两类目录下全部 `.json` 文件（递归）。
- **解析**：对每个 JSON，读取根级或 `events` 数组；遍历每个事件对象，取出 `characters` 字段。
- **类型处理**：`characters` 既可能是 **字符串列表**，也可能是 **单个字符串**；统一拆成若干条 **非空 mention 字符串**（strip 去空白）。
- **聚合指标**：
  - **occurrence_count**：该 mention 在「事件条目」中出现的次数（按事件计数，不是按字数）。
  - **file_count**：该 mention 出现在多少个 JSON 文件中。
- **来源维度（source）**：根据文件路径归属判定：
  - 路径位于 `hongloumeng_txt_json` → `txt`
  - 路径位于 `hongloumeng_json` → `video`
  - 同一名称在两类来源分别计数，输出中带 `source` 列，便于后续知识库标注「文本 / 影像」证据来源。

### 4.2 实现脚本

- `scripts/extract_characters_to_csv.py` → `all_characters.csv`  
（地点同类逻辑见 `extract_locations_to_csv.py`，输出 `all_locations.csv`，与本人物归一并行，不进入人物映射主链。）

### 4.3 性质说明

本阶段为 **确定性统计算法**，无学习过程；复杂度与「JSON 文件数 × 平均每文件事件数」线性相关。

## 五、阶段 B：规则分类（Mention Type）

### 5.1 目的

在进入昂贵且易不确定的 LLM 之前，用 **可解释的规则** 将每条 mention 分为四类，缩小需模型处理的集合，并 **显式保留** 不应归一的类型。

### 5.2 类别定义

| mention_type | 含义 |
|--------------|------|
| `canonical` | 与人物表 **`姓名` 完全一致**（精确字符串匹配） |
| `alias` | 可能是别称、简称、关系称呼，**交首次 LLM 映射** |
| `generic` | 泛称、职业/身份总名、群体指代等，**不适合与单一标准人物一一对应** |
| `visual_noise` | 剧版中偏 **衣着、外貌、路人** 等视觉描述，**不适合作为稳定人物 ID** |

### 5.3 判定算法（决策序 / 优先级）

对每条 mention 字符串 `m`（经过 strip）执行 **有序判断**（**先命中先分类**，不再向下游规则覆盖）：

1. **精确集合匹配**  
   - 若 `m ∈ CanonicalNames`（来自 CSV 的 `姓名` 列构成的集合），则 **`canonical`**。  
   - **算法**：哈希集合查找，平均 \(O(1)\)。

2. **视觉噪声模式集**（正则 / 关键词）  
   - 例如含「路人」、颜色 + 衣着 + 男女类描述、「年轻女子 / 妇人 / 男子」等模式。  
   - **命中** → **`visual_noise`**，并记录 `rule_note` 便于审计。

3. **泛称模式集**  
   - **注意**：职业词采用 **整词锚定**（如 `^道士$`、`^嬷嬷$`），避免「张道士」「李嬷嬷」等 **具体人物** 被后缀误判为泛称。  
   - 群体词如「众人」「众姑娘」「…们」等。  
   - **命中** → **`generic`**。

4. **默认**  
   - 未命中上述规则 → **`alias`**，进入下游 LLM。

### 5.4 性质说明

这是典型的 **基于规则的层次化分类器**（**decision list / cascading rules**），非机器学习；优点是 **可解释、可单元测试、可逐步加规则**。

### 5.5 实现脚本与产物

- `知识库/character_normalization_pipeline.py`
- 输出：`mentions_classified.csv`、`classification_stats.json`、`alias_for_llm.csv/json`、`llm_normalization_input.json`、`llm_prompt_template.txt` 等。

## 六、阶段 C：首次大模型归一（映射到现有标准表）

### 6.1 任务定义

对 **`mention_type == alias`** 的每条记录，调用大模型，输出：

- `canonical_name`：**必须**为「当前人物表中的某一 `姓名`」**字符串完全一致**，或 **`unknown`**；
- `confidence`：`high` / `medium` / `low`；
- `reason`：简短中文理由（便于人工复核）。

### 6.2 约束策略（提示词工程）

- **封闭词表**：在 prompt 中注入完整 **`candidate_canonical_names`** 列表，要求模型 **禁止**输出列表外姓名。
- **歧义与安全**：对「二爷」「老太太」「太太」等 **高歧义** 称谓，提示词要求 **把握不足则 unknown**。
- **泛称不回写**：已在阶段 B 侧重的泛称 / 视觉项原则上不进入本列表；若进入，模型也应标为 `unknown`。

### 6.3 工程方法

- **调用方式**：与 `红楼梦文本/deal_txt.py` 一致，使用 **DashScope** `MultiModalConversation`，**纯文本 user 消息**（无需视频）。
- **批处理（batching）**：为防止单次上下文过长或超时，将 alias 列表按固定 **batch_size**（如 45）切分；每批独立请求，**校验**返回 JSON 中 `results` 条数与输入条数一致、字段合法。
- **校验后处理**：对 `canonical_name` 做 **集合成员检查**（或 `unknown`）；`confidence` 枚举校验。
- **断线续跑（实现上）**：可写 partial 结果与 raw 日志，降低长任务失败成本。

### 6.4 产物

- `mention_normalization_llm.json`：顶层 `{"results": [...]}`  
- `mention_normalization_llm.raw.txt`：各批模型原始文本，便于排查解析失败或偏题。

### 6.5 方法归类

综合为 **约束生成（constrained decoding 的提示词近似）** + **分片归并（map 式批处理）** + **确定性 JSON 校验**。

## 七、阶段 D：人物表增补（针对表不完备与 unknown）

### 7.1 动因

首次归一严格要求 **只能从现表选择**，因此像 **「周瑞」** 等原著确有其人但 **未录入人物表** 的 mention 会被标为 **`unknown`**。这与「模型未起作用」无关，而是 **词表封闭** 的必然结果。

### 7.2 方法

1. **输入提取**：从 `mention_normalization_llm.json` 中筛出 **`canonical_name == "unknown"`** 的条目；按 **`mention` 去重**，合并多条理由为 `first_pass_reasons`，减少重复调用。
2. **二次 LLM 判别**（独立 prompt）：对每条 unknown，判定：
   - **`append_to_table`**：《红楼梦》中 **可单独立条**、有稳定所指的人物（含重要仆役等）→ 生成 **`姓名`、`人物简介`、`首次出场回目`、`备注`**；
   - **`reject`**：泛称、无特指职业、群体、视觉描述等 → **不写表**。
3. **写入策略**：通过校验的行 **追加** 写入 `红楼梦人物表.csv`；运行前备份 **`红楼梦人物表.csv.bak`**。
4. **防重复**：若模型给出的 **`姓名`** 已在表中存在，则 **拒绝写入**并记录原因。

### 7.3 产物

- `character_table_enrichment_log.json`：增补决策与追加行清单  
- `character_table_enrichment.raw.txt`：模型原始输出  

### 7.4 性质说明

这是 **人机协同的数据库扩充（human-in-the-loop schema extension）**：模型提案，规则与集合成员检查守门，**强烈建议人工抽查**后再锁定版本。

## 八、阶段 E：聚合为人物知识库 JSON（character_kb）

### 8.1 目标结构

与 `sample_character_kb.json` 对齐，每条记录形如：

```json
{
  "canonical_name": "<标准姓名>",
  "aliases": ["<别称1>", "<别称2>", ...],
  "sources": ["txt", "video"],
  "notes": "<聚合说明>"
}
```

### 8.2 聚合算法

1. **输入**：`mention_normalization_llm.json` 中所有 **`canonical_name` 非空且不为 `unknown`** 的映射。
2. **分组键**：`canonical_name`。
3. **别称集合**：对该标准名下的所有 **`mention`**，若 **`mention ≠ canonical_name`**，则加入 **aliases**（集合去重）；若仅存在「标准名映射到自身」且无别称，则 **aliases 为空数组 `[]`**。
4. **来源（sources）**：辅助读取 `alias_for_llm.json`，按 **`character` 字段** 与 **别称字符串** 对齐，汇总该别称在 **txt / video** 是否出现，写入 `sources` 列表（固定顺序 `txt`, `video`）。
5. **notes**：对同一标准名下多条映射的 **`reason`** 去重、排序、截断拼接，标明由 `mention_normalization_llm` 聚合，便于追溯（可人工精简）。

### 8.3 复杂度

设成功映射条数为 \(M\)，标准名去重后为 \(K\)，则聚合为 **\(O(M)\)** 分组累加；别称来源合并依赖 alias 索引，可为 **\(O(M)\)** 或 **\(O(M \log M)\)**（取决于实现）。

### 8.4 实现脚本

- `知识库/build_character_kb_from_normalization.py` → `character_pipeline_out/character_kb.json`

## 九、关联流程（与本主链衔接但可独立）

### 9.1 剧版 JSON 英文字段复检

- **方法**：对 `events` 内 **内容字段值**（如 `characters`、`action`、`event_summary` 等）用 **正则 `[A-Za-z]`** 检测；**排除** JSON 键名自带的英文。
- **用途**：筛出需用 `deal_video.py` 对 **视频片段** 重跑的条目（非对 JSON 直接改）。

### 9.2 文本章节过长与分段

- **方法**：按 **段落** 切分，在 **字数接近半数** 的候选切分点上，用 **打分函数** 综合「距目标长度距离」与 **边界质量**（句末、叙事起笔词如「且说」「次日」等），选取较优切分；生成 `第XXX_1回.txt`、`第XXX_2回.txt`。
- **用途**：降低单次 LLM 超时；`deal_txt.py` 支持 **分段调用后合并事件** 并 **重编 event_id**。

### 9.3 地点抽取

- 与人物对称，从 `location` 字段聚合到 `all_locations.csv`（含 `source`），供地点归一或时间线项目使用。

## 十、质量保障与人工审核建议

| 环节 | 建议 |
|------|------|
| 规则分类 | 定期根据 `mentions_classified.csv` 抽样，调整 **泛称 / 视觉** 正则，减少误判 |
| 首次 LLM | 对 `confidence: low`、涉及 **高歧义称谓** 的映射重点抽查 |
| 人物表增补 | **必查** `character_table_enrichment_log.json`，核对史实与姓名用字 |
| 最终 KB | 检查 **一对多 / 多对一** 是否合理（如别名是否误并） |

## 十二、小结

本流水线在工程上融合了：

1. **确定性统计与集合操作**（mention 抽取与计数、按标准名分组）；  
2. **层次化规则分类**（decision list，可解释）；  
3. **闭词表约束下的大模型映射**（提示词约束 + 批处理 + JSON 校验）；  
4. **二次判别与 CSV 追加**（表外人物的安全扩充）；  
5. **聚合与溯源字段**（`character_kb.json` + notes / sources）。

整体定位是 **半自动、可审计、可迭代** 的人物知识库构建路径，而非一次性无监督端到端映射。
